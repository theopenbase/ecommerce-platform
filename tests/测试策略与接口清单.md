### 2.3 关键测试策略

#### 2.3.1 订单模块（最高优先级）

- **幂等性**：重复提交 CreateOrder 必须返回相同结果，不产生重复订单

- **状态机**：订单状态转换路径正确（待付款→已取消/待发货→待收货→已完成）
- **分布式事务**：支付成功事件触发积分、优惠券等后续链路

#### 2.3.2 支付链路（支付服务完成前，使用 Mock）

- 支付回调 mock，验证订单状态更新正确
- 退款申请流程验证

#### 2.3.3 用户模块

- JWT Token 有效性：过期/篡改/注销 token 正确拒绝
- 收货地址：上限检查（地址数量限制）、默认地址逻辑、CRUD 正确性
- 会员积分：余额计算、流水记录

#### 2.3.4 商品模块

- 商家接口：shop_id 归属校验，非本店商品禁止操作

## 3. Frank 评审高风险项（必测）

> 来源：Frank 评审遗留清单，以下高风险项需在集成测试阶段重点覆盖。

### 3.1 高风险（必测）

#### R-1：Redis/DB 库存不同步 — 超卖风险 🔴

**风险描述**：CreateOrder 中 FreezeStock 使用 Redis 原子扣减，但无 DB 层库存同步机制。超卖漏洞。

**测试策略**：
- 库存预占（FreezeStock）与最终扣减（DeductStock）之间的数据一致性
- Redis 宕机场景：库存数据是否持久化到 DB
- 并发下单：多个请求同时扣减 Redis 库存，验证 Lua 脚本原子性

**测试用例**：
```
T-1: 并发10个请求同时扣减同一SKU，验证库存不出现负数
T-2: Redis FreezeStock 成功后 DB 写入失败，验证订单回滚
T-3: 库存仅剩1件，10个并发请求全部到达，验证仅1单成功
```

**优先级**：P0

---

#### R-2 & R-7：订单无数据库事务包装 — 失败回滚风险 🔴

**风险描述**：CreateOrder 中 CreateParentOrder → CreateSubOrder → CreateOrderItems 为串行 DB 写入，无事务包装，任一步骤失败无法回滚。

**Charlie 确认（2026-05-02）**：R-7 为 P1遗留，当前无事务包装。

**测试用例**：
```
T-4: CreateSubOrder 失败，验证 parent_order 存在（孤儿记录）→ 需补充事务
T-5: CreateOrderItems 失败，验证 parent_order 和 sub_order 均存在（不完整订单）
T-6: DB 连接中断场景，验证无孤儿订单记录
T-6a: FreezeStock 部分成功 → 验证已冻结库存回滚（应用层补偿）
```

**优先级**：P1遗留（待事务修复）

---

#### R-3：支付密码校验缺失 🔴

**风险描述**：ApplyRefund 中未校验支付密码，任一买家均可申请退款。

**Bob 产品决策（2026-05-02）— 按阈值分层**：
- 退款金额 ≤ 200元（含）：仅登录态验证，无需支付密码
- 退款金额 > 200元：强制验证支付密码

**测试用例**：
```
T-7a: 小额退款（≤200元）无支付密码 → 通过
T-7b: 小额退款（0元，如仅退优惠券）无支付密码 → 通过
T-8a: 大额退款（>200元）无支付密码 → ErrPayPasswordNotSet
T-8b: 大额退款（>200元）密码错误 → ErrIncorrectPayPassword
T-9:  大额退款（>200元）密码正确 → 退款正常受理
T-9a: seller 审批退款（任意金额）→ 无需密码，直接处理
T-9b: 边界：200元退款 → 无需密码（≤200元免密）
T-9c: 边界：201元退款 → 需要密码（>200元需验密）
```

**优先级**：P0（Bob 已确认产品流程）

---

### 3.2 中风险（覆盖）

#### R-4：幂等检查非原子性 — 并发重复下单 🟡

**风险描述**：CheckIdempotencyKey → CacheIdempotencyKey 之间存在时间窗口，并发请求可绕过幂等检查。

**测试策略**：
- 并发压测：同一用户同时发送 N 个相同订单请求，验证不产生 N 个订单
- 分布式环境（多实例）下幂等性验证

**测试用例**：
```
T-10: 10个并发 CreateOrder 请求（相同 Items），验证仅1单成功，其余返回 ErrIdempotentKeyUsed
T-11: 幂等 key 过期后（10分钟），验证可重新下单
```

**优先级**：P1

---

#### R-5：ListGoods JOIN 错误 — 多SKU场景漏显示 🟡

**风险描述**：商品列表查询若 SPU 关联多个 SKU，JOIN 错误可能导致重复行或漏显示。

**测试策略**：
- 创建多 SKU 商品，验证列表仅返回1条 SPU 记录
- 不同店铺同一商品名的去重验证

**测试用例**：
```
T-12: SPU 关联3个 SKU，ListGoods 返回1条 SPU，验证 SKU 数量≥1
T-13: 同名商品跨店铺查询，验证每 SPU 仅出现一次
```

**优先级**：P1

---

#### R-6：品牌授权表未实现 — 类目资质动态校验 🟡

**风险描述**：CreateSpu 未校验品牌授权，非授权店铺可创建任意品牌商品。

**Bob 产品决策（2026-05-02）— 按类目资质动态判断**：
- 系统读取末级类目「类目资质要求」，若含「品牌授权文件」则 CreateSpu 必须上传 brand_authorization 凭证，否则阻断
- 若类目无品牌资质要求，则不校验

**测试用例**：
```
T-14a: 有资质要求类目 + 上传授权凭证 → 通过
T-14b: 有资质要求类目 + 无授权凭证 → 阻断（ErrBrandAuthRequired）
T-14c: 无资质要求类目 + 无授权凭证 → 通过
T-14d: 有资质要求类目（多文件） + 部分文件缺失 → 阻断
T-14e: 非末级类目有资质要求 → 不触发校验（仅末级类目判断）
```

**优先级**：P2（需系统实现类目资质读取和凭证校验逻辑）
